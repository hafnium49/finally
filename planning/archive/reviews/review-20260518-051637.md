# Review: changes since last commit

## Findings

1. **Low - FastAPI lifespan example is not runnable as written** (`planning/MARKET_INTERFACE.md:106`, `planning/MARKET_INTERFACE.md:116`, `planning/MARKET_INTERFACE.md:184`)

   The lifecycle sample calls `await source.start(initial_tickers=["AAPL", "GOOGL", ...])`, and later says callers must `await source.start(initial_tickers)`, but the shipped interface is `start(tickers: list[str])` and does not define an `initial_tickers` keyword (`backend/app/market/interface.py:26`). The same sample creates `cache` inside `lifespan()` and then references `cache` at module scope in `app.include_router(create_stream_router(cache))`, which would raise `NameError` if copied directly.

   Suggested fix: use `await source.start(["AAPL", "GOOGL", ...])` and either mark the block as pseudocode or restructure it so the router receives a cache that is actually in scope.

2. **Low - `PriceCache.remove()` version behavior is documented inconsistently** (`planning/MARKET_INTERFACE.md:159`, `planning/MARKET_INTERFACE.md:169`, `planning/MARKET_INTERFACE.md:318`)

   The version-counter section says both `update()` and `remove()` bump `version`, and the test matrix says `test_cache.py` pins version advancement on `update`/`remove`. Later, the same document says `remove(ticker)` does not bump `version`. The latter matches the shipped implementation: `PriceCache.remove()` only pops the ticker and does not increment `_version` (`backend/app/market/cache.py:59`). The current test only asserts version increments for `update()` calls (`backend/tests/market/test_cache.py:60`).

   Suggested fix: if silent removal is intentional, update the version-counter section and test matrix to say only `update()` advances `version`; otherwise change the implementation and tests together.

3. **Low - `MASSIVE_API.md` claims SSE keepalives are implemented when they are still a gap** (`planning/MASSIVE_API.md:321`)

   `MASSIVE_API.md` says "The keepalive comment fires every 15 s", but `_generate_events()` currently emits only the initial `retry:` directive and price `data:` events when the cache version changes (`backend/app/market/stream.py:61`, `backend/app/market/stream.py:75`). `MARKET_INTERFACE.md` correctly calls keepalive comments a gap (`planning/MARKET_INTERFACE.md:238`), so the two new docs contradict each other and the shipped stream behavior.

   Suggested fix: reword the Massive API doc to describe keepalives as planned work, or implement timed keepalive comments in `stream.py`.

4. **Low - Massive package version wording conflicts with the locked project dependency** (`planning/MASSIVE_API.md:5`)

   The doc says the `massive` package is current as of May 2026 at `v2.7.0`, while this checkout is locked to `massive==2.2.0` (`backend/uv.lock:269`). Since the file is framed as reference documentation "as used in FinAlly" (`planning/MASSIVE_API.md:3`), readers may assume examples and attribute mappings were validated against the installed project version.

   Suggested fix: distinguish the upstream latest release from the locked FinAlly version, or intentionally update the lockfile if the newer SDK is required.

5. **Low - Threading rationale describes a write path the shipped Massive client does not use** (`planning/MARKET_INTERFACE.md:153`, `planning/MARKET_INTERFACE.md:155`)

   The document justifies `threading.Lock` by saying a cache write can be in flight from a non-event-loop thread because Massive runs `RESTClient` inside `asyncio.to_thread(...)`. In the shipped client, only `_fetch_snapshots()` runs in the worker thread; `PriceCache.update()` is called after `await asyncio.to_thread(...)` returns, back on the event loop (`backend/app/market/massive_client.py:97`, `backend/app/market/massive_client.py:104`). The lock choice is still reasonable, but the stated rationale can mislead future contributors about where cache mutations occur.
