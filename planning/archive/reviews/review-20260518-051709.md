# Review: changes since last commit

Scope: untracked documentation changes since `HEAD`, focused on `planning/MARKET_INTERFACE.md` and `planning/MASSIVE_API.md`. Existing generated review files were treated as prior review artifacts, not product changes.

## Findings

### P2 - Historical price storage is described as shipped, but no backend implementation exists

- `planning/MASSIVE_API.md:124` says the shipped backend writes to its own `price_ticks` table.
- `planning/MARKET_INTERFACE.md:251` says `/api/prices/history/{ticker}` is served from a SQLite `price_ticks` table written by a background task.
- The actual backend has no `price_ticks` table, no SQLite layer, and no `/api/prices/history` route; `rg "price_ticks|prices/history" backend` only finds demo/history comments unrelated to the planned API.

This can mislead the next implementer into wiring frontend/history behavior against a nonexistent backend surface. These sections should clearly say "planned" until the table, writer, retention job, and route are implemented.

### P2 - Keepalive behavior is documented both as missing and as active

- `planning/MARKET_INTERFACE.md:238` correctly calls SSE keepalive comments a gap in `stream.py`.
- `planning/MASSIVE_API.md:321` then states "The keepalive comment fires every 15 s".
- Actual `backend/app/market/stream.py:61-85` emits the `retry` directive and data on `PriceCache.version` changes only; it does not emit idle `: keepalive` comments.

The false statement hides a deployment risk behind proxies that close idle SSE connections. Either remove the active-behavior wording from `MASSIVE_API.md` or implement keepalives in `stream.py`.

### P2 - Lifecycle sample does not match the implemented API

- `planning/MARKET_INTERFACE.md:106` calls `await source.start(initial_tickers=[...])`, but `MarketDataSource.start` and both implementations accept `tickers`, not `initial_tickers` (`backend/app/market/interface.py:25-31`, `backend/app/market/massive_client.py:41`, `backend/app/market/simulator.py:219`).
- `planning/MARKET_INTERFACE.md:116` calls `app.include_router(create_stream_router(cache))` outside the lifespan function, where `cache` is not in scope in that snippet.

Copying this example would fail at application startup. Use `await source.start(["AAPL", ...])` and create/include the router from a cache object that exists at module construction time, or restructure the sample to show a valid FastAPI pattern.

### P3 - Version-counter documentation contradicts the cache implementation

- `planning/MARKET_INTERFACE.md:159` says both `update()` and `remove()` bump `version`.
- `planning/MARKET_INTERFACE.md:169` says `remove(ticker)` does not bump `version`.
- The test matrix at `planning/MARKET_INTERFACE.md:318` again says `test_cache.py` pins version advancement on `update`/`remove`.
- Actual `PriceCache.remove` only pops the ticker and does not change `_version` (`backend/app/market/cache.py:59-63`); tests only assert update increments (`backend/tests/market/test_cache.py:60-67`).

The implementation appears intentionally silent on removal, so the docs and test matrix should consistently state that only updates currently advance the SSE version.

### P3 - Massive package version claim disagrees with the project lockfile

- `planning/MASSIVE_API.md:5` says the current PyPI package is `massive` v2.7.0.
- The checked-in lockfile resolves `massive` to v2.2.0 (`backend/uv.lock:269-270`).

If these docs are meant to describe the shipped client, pin examples and API caveats to the locked version or note that the version statement refers to an externally verified latest release rather than what this repo installs.
