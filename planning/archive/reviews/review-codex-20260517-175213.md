# Review of planning/PLAN.md

## Findings

### High: There is no state refresh contract after trades or chat-driven mutations

`planning/PLAN.md:287-307` defines only one push channel, `/api/stream/prices`, and `POST /api/chat` returns only `message + executed actions`. But chat can execute trades and watchlist changes (`planning/PLAN.md:331`), and manual trades mutate cash/positions (`planning/PLAN.md:294`). The frontend also promises live portfolio total, cash balance, positions, watchlist, and P&L views (`planning/PLAN.md:448-455`).

The plan does not say how sibling UI panels learn that cash changed, a position was created, or a ticker was added by the LLM. Without this, frontend and backend agents can both implement reasonable but incompatible behavior.

Recommendation: pick one v1 rule explicitly. The simplest is: after any successful `POST /api/portfolio/trade` or `POST /api/chat`, the frontend refetches `/api/portfolio`, `/api/watchlist`, and any visible history endpoint affected by the action. Even better, have both mutation endpoints return `portfolio` and `watchlist` snapshots using the same response shapes as the GET endpoints.

### High: Portfolio valuation breaks if a held ticker is removed from the watchlist

The market source polls "the union of all watched tickers" (`planning/PLAN.md:175`), `price_ticks` are written for tickers in watchlists (`planning/PLAN.md:258`), and `DELETE /api/watchlist/{ticker}` is documented as just removing a ticker (`planning/PLAN.md:302`). Positions are separate from the watchlist, so a user can buy NFLX and then remove NFLX from the watchlist.

At that point portfolio valuation, unrealized P&L, position display, snapshots, and chart history need a current NFLX price, but the plan no longer requires the market subsystem to track it. The existing market sources also remove the ticker from the cache on remove, so this is not theoretical implementation noise.

Recommendation: define the tracked ticker set as `watchlist tickers UNION positions.ticker`. Removing a ticker from the watchlist should only stop showing it in the watchlist; it should not stop market-data tracking while a position exists.

### Medium: Core REST response shapes are not specified

The endpoint table in `planning/PLAN.md:287-307` gives descriptions, but not stable JSON contracts for most endpoints. Missing examples include:

- `GET /api/portfolio`: exact names for cash, total value, unrealized P&L, positions, market value, current price, and percent change.
- `POST /api/portfolio/trade`: success body, error body, status codes, and whether it reuses the chat `actions` trade shape.
- `GET /api/portfolio/history`: range support, row fields, ordering, and empty-history behavior.
- `GET /api/prices/history/{ticker}`: row fields, range semantics, max row count, and unknown ticker behavior.
- `POST /api/chat`: request body and whether the response includes only `message/actions` or refreshed application state.

This is a parallel-agent risk. Add compact JSON examples or typed schemas to section 8 before frontend and backend work proceed independently.

### Medium: Conversation summary persistence is required but left as an implementation choice

Section 9 requires a rolling summary for messages older than the last 10 and says it must survive requests (`planning/PLAN.md:337-341`). The schema only defines `chat_messages` (`planning/PLAN.md:267-273`), then leaves summary storage as either a `chat_state` row or JSON in `users_profile`.

That fork will produce incompatible implementations. Pick one storage contract. A simple option:

```sql
CREATE TABLE chat_state (
  user_id TEXT PRIMARY KEY,
  summary TEXT NOT NULL DEFAULT '',
  summary_message_count INTEGER NOT NULL DEFAULT 0,
  updated_at TEXT NOT NULL
);
```

Also define a max summary length and mock-mode behavior for the summarizer.

### Medium: The LLM instructions depend on non-portable agent context and conflict with first-launch UX

The plan tells implementers to use a `cerebras-inference` skill (`planning/PLAN.md:318` and `planning/PLAN.md:329`). That is not a project dependency or generally available agent capability, so the shared plan should not require it for core product behavior.

Separately, the first-launch UX promises an AI chat panel ready to assist (`planning/PLAN.md:20`), while `OPENROUTER_API_KEY` is marked required (`planning/PLAN.md:135-137`). The plan does not say whether the backend refuses to start, chat returns a friendly 503, or missing keys imply mock mode.

Recommendation: replace the skill instruction with concrete implementation requirements: LiteLLM dependency, model string, OpenRouter provider configuration, structured output invocation, timeout/retry policy, and mock fallback. Then specify missing-key behavior explicitly.

### Medium: SSE event shape is ambiguous and likely to split frontend/backend implementations

Section 6 says each SSE event contains a single `ticker`, `price`, `previous_price`, `timestamp`, and direction (`planning/PLAN.md:198`). The current backend market stream emits one event containing a dictionary of all cached tickers. Both are defensible designs, but the plan needs to choose one and show the literal `data:` JSON payload.

If the intended contract is batched events, document that the frontend receives:

```json
{
  "AAPL": {"ticker": "AAPL", "price": 190.5, "previous_price": 190.1, "timestamp": 123, "change": 0.4, "direction": "up"}
}
```

If the intended contract is one event per ticker, update the backend requirements and tests accordingly.

### Medium: Malformed LLM output handling is tested but not specified

The test plan mentions graceful handling of malformed LLM responses (`planning/PLAN.md:530`), but section 9 never defines the behavior. Implementers need to know whether to retry, return HTTP 502, persist the user message, synthesize an assistant message, or surface a frontend error.

Recommendation: define a policy such as: retry once on malformed structured output; if it still fails, persist the user message, do not execute actions, return a synthetic assistant response with `actions: []`, and log the raw invalid response at warning level.

### Medium: The cloud auth warning suggests an approach that can break SSE

The deployment warning recommends a shared-secret header or basic-auth shim on `/api/*` (`planning/PLAN.md:517`). Browser `EventSource` cannot attach arbitrary custom headers, so a shared-secret header applied to all `/api/*` routes will break `/api/stream/prices`.

Recommendation: document this constraint. For local demos exposed beyond localhost, prefer basic auth, cookie-based auth, or route-specific handling that keeps EventSource compatible.

### Low: Section 13 should not remain in the active implementation contract

Section 13 is described as a working list to triage before implementation (`planning/PLAN.md:557-559`), but most entries are already marked resolved. Its final insight block still says the chat/trade boundary and SSE behavior are underspecified (`planning/PLAN.md:617-620`), even though earlier sections now define parts of those contracts.

This creates a document-hygiene hazard: future agents may reopen resolved choices or treat stale notes as current requirements. Move section 13 to `planning/archive/`, or rewrite it as a short resolved-decisions appendix with only genuinely open items.

### Low: The directory tree reads as current state but includes missing scaffold

The tree lists `frontend/`, `scripts/`, `test/`, `db/`, `Dockerfile`, `docker-compose.yml`, and `.env.example` (`planning/PLAN.md:89-116`). Those are reasonable target deliverables, but several are not present in the current repository.

Recommendation: label section 4 as "Target Directory Structure" or add a "Current repo status" note so agents do not assume scaffolding already exists.

## Open Questions

- Should `POST /api/chat` return refreshed portfolio/watchlist snapshots, or should the frontend always refetch after the chat call?
- Should manual trade responses use the same shape as chat `actions[]` entries, or a richer portfolio-specific response?
- Should `session_anchor_price` reset on backend restart by design, or should anchors be persisted for the process/session day?

## Summary

The plan is coherent at the product level, and the biggest architectural choices are reasonable. The remaining risk is contract precision: state refresh after mutations, tracked ticker ownership, API payload shapes, chat summary storage, and LLM failure behavior need concrete decisions before multiple agents implement against this file.

No test suite was run for this documentation review.
