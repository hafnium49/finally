# SCHEMA.md — FinAlly Database Schema (Phase 1 contract)

This document is the canonical schema contract for the FinAlly backend. It is owned by the **Database Engineer** and consumed read-only by the Backend API Engineer and LLM Engineer.

Source of truth: `planning/PLAN.md` §7 (tables/columns) and §9 (`actions` JSON shape). Where PLAN.md is silent or ambiguous, this file picks the conservative interpretation and flags it inline.

All identifiers are `TEXT` (UUIDv4 strings, generated by `uuid.uuid4().hex` or `str(uuid.uuid4())`). All timestamps are ISO 8601 strings produced via `datetime.now(timezone.utc).isoformat()`. All quantity / cash / price columns are `REAL` because fractional shares are first-class.

---

## 1. Table definitions

All `CREATE TABLE` statements use `IF NOT EXISTS` so that `init_database()` is idempotent.

### 1.1 `users_profile`

User state. Single-user for v1, but keyed by `id` so multi-user is a row-insert away.

```sql
CREATE TABLE IF NOT EXISTS users_profile (
    id           TEXT PRIMARY KEY DEFAULT 'default',
    cash_balance REAL NOT NULL DEFAULT 10000.0,
    created_at   TEXT NOT NULL
);
```

> Note: PLAN.md §7 lists only `id`, `cash_balance`, `created_at` for this table. Unlike every other table, `users_profile` does **not** carry a separate `user_id` column — its `id` *is* the user identifier. Other tables' `user_id` foreign-references this `id` by convention (not enforced with `FOREIGN KEY` to keep init order trivial and avoid CASCADE surprises during seed).

### 1.2 `watchlist`

Tickers the user is watching.

```sql
CREATE TABLE IF NOT EXISTS watchlist (
    id       TEXT PRIMARY KEY,
    user_id  TEXT NOT NULL DEFAULT 'default',
    ticker   TEXT NOT NULL,
    added_at TEXT NOT NULL,
    UNIQUE (user_id, ticker)
);
```

### 1.3 `positions`

Current holdings. One row per `(user_id, ticker)`.

```sql
CREATE TABLE IF NOT EXISTS positions (
    id         TEXT PRIMARY KEY,
    user_id    TEXT NOT NULL DEFAULT 'default',
    ticker     TEXT NOT NULL,
    quantity   REAL NOT NULL,
    avg_cost   REAL NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE (user_id, ticker)
);
```

### 1.4 `trades`

Append-only trade history.

```sql
CREATE TABLE IF NOT EXISTS trades (
    id          TEXT PRIMARY KEY,
    user_id     TEXT NOT NULL DEFAULT 'default',
    ticker      TEXT NOT NULL,
    side        TEXT NOT NULL CHECK (side IN ('buy', 'sell')),
    quantity    REAL NOT NULL,
    price       REAL NOT NULL,
    executed_at TEXT NOT NULL
);
```

> Note: PLAN.md §7 lists `side` as `"buy"` or `"sell"`; the `CHECK` constraint enforces this at the storage layer so a buggy caller cannot smuggle in a malformed side.

### 1.5 `portfolio_snapshots`

Portfolio total value over time. Written every 30s by a background task and immediately after each trade.

```sql
CREATE TABLE IF NOT EXISTS portfolio_snapshots (
    id          TEXT PRIMARY KEY,
    user_id     TEXT NOT NULL DEFAULT 'default',
    total_value REAL NOT NULL,
    recorded_at TEXT NOT NULL
);
```

### 1.6 `price_ticks`

Persisted price history for the main chart. Written ~every 5s per watched ticker, independent of SSE cadence. Retention: 7 days; older rows pruned by a daily background task. Tick history is global (not per-user) — price data is the same for everyone.

```sql
CREATE TABLE IF NOT EXISTS price_ticks (
    ticker      TEXT NOT NULL,
    price       REAL NOT NULL,
    recorded_at TEXT NOT NULL,
    PRIMARY KEY (ticker, recorded_at)
);
```

### 1.7 `chat_messages`

Conversation history with the LLM. `actions` is JSON-encoded text; see §3 for the shape. `actions` is `NULL` for messages where `role = 'user'`.

```sql
CREATE TABLE IF NOT EXISTS chat_messages (
    id         TEXT PRIMARY KEY,
    user_id    TEXT NOT NULL DEFAULT 'default',
    role       TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
    content    TEXT NOT NULL,
    actions    TEXT,
    created_at TEXT NOT NULL
);
```

### 1.8 `chat_state`

Rolling conversation summary referenced by PLAN.md §9 "Conversation Context Window". One row per user.

```sql
CREATE TABLE IF NOT EXISTS chat_state (
    user_id    TEXT PRIMARY KEY DEFAULT 'default',
    summary    TEXT NOT NULL DEFAULT '',
    updated_at TEXT
);
```

> Note: `updated_at` is nullable because the seed row is inserted before any LLM summarization has occurred. It is set the first time `summary` is rewritten.

## 2. Indexes

```sql
-- Pruning support for the 7-day retention job (PLAN.md §7 `price_ticks`).
CREATE INDEX IF NOT EXISTS idx_price_ticks_recorded_at
    ON price_ticks(recorded_at);

-- /api/portfolio/history sorts/filters by recorded_at; supports range queries.
CREATE INDEX IF NOT EXISTS idx_portfolio_snapshots_user_recorded
    ON portfolio_snapshots(user_id, recorded_at);

-- /api/chat replays history per user in chronological order.
CREATE INDEX IF NOT EXISTS idx_chat_messages_user_created
    ON chat_messages(user_id, created_at);

-- Trade history queries (e.g. blotter, debugging) filter by user.
CREATE INDEX IF NOT EXISTS idx_trades_user_executed
    ON trades(user_id, executed_at);
```

The `UNIQUE (user_id, ticker)` constraints on `watchlist` and `positions` are already backed by implicit unique indexes, so no extra index is required for ticker lookups within a user.

## 3. `chat_messages.actions` JSON shape

This block is copied verbatim from PLAN.md §9 "Backend Response & `actions` Shape" and is the binding contract between the LLM Engineer (writes it), the Backend API Engineer (serves it), and the Frontend Engineer (renders it).

The full backend chat response wraps the LLM message with a resolved `actions` array describing what actually happened:

```json
{
  "message": "I've added 10 shares of AAPL and put PYPL on the watchlist.",
  "actions": [
    {
      "kind": "trade",
      "status": "ok",
      "ticker": "AAPL",
      "side": "buy",
      "quantity": 10,
      "fill_price": 192.34,
      "cash_after": 8076.60
    },
    {
      "kind": "trade",
      "status": "error",
      "ticker": "TSLA",
      "side": "buy",
      "quantity": 50,
      "error": "insufficient_cash",
      "error_message": "Need $12,400 but only $8,076.60 available."
    },
    {
      "kind": "watchlist",
      "status": "ok",
      "ticker": "PYPL",
      "action": "add"
    }
  ]
}
```

Field-level rules (verbatim from PLAN.md §9):

- `kind`: `"trade"` or `"watchlist"`
- `status`: `"ok"` or `"error"`
- Trade entries always include `ticker`, `side`, `quantity`; on success also `fill_price` and `cash_after`; on failure also `error` (machine code) and `error_message` (human text)
- The same `actions` array is persisted in `chat_messages.actions` so the chat panel can re-render history accurately on reload

What gets stored in the `chat_messages.actions` column is **the JSON array only** (the value of the top-level `actions` key above), serialized via `json.dumps(...)`. It is `NULL` for rows where `role = 'user'` and for assistant rows that performed no trades and no watchlist changes (this is the conservative reading of PLAN.md §7's "null for user messages" — assistant rows with an empty action list MAY store `[]` instead; both are acceptable but the LLM Engineer should pick one and stick to it).

### Success example (assistant row, `actions` column)

```json
[
  {
    "kind": "trade",
    "status": "ok",
    "ticker": "AAPL",
    "side": "buy",
    "quantity": 10,
    "fill_price": 192.34,
    "cash_after": 8076.60
  },
  {
    "kind": "watchlist",
    "status": "ok",
    "ticker": "PYPL",
    "action": "add"
  }
]
```

### Error example (assistant row, `actions` column)

```json
[
  {
    "kind": "trade",
    "status": "error",
    "ticker": "TSLA",
    "side": "buy",
    "quantity": 50,
    "error": "insufficient_cash",
    "error_message": "Need $12,400 but only $8,076.60 available."
  }
]
```

The defined `error` machine codes (per PLAN.md §9 "Trade Execution & Validation") are:

- `insufficient_cash` — buy would overdraw the cash balance
- `insufficient_shares` — sell exceeds current position quantity
- `unknown_ticker` — ticker not recognized by the active market data source

## 4. Default seed data

Seed data is inserted with `INSERT OR IGNORE` so re-running init is a no-op once rows exist. `:created_at` / `:added_at` are bound at call time as the current UTC ISO 8601 timestamp.

```sql
-- 4.1 Default user profile (PLAN.md §7).
INSERT OR IGNORE INTO users_profile (id, cash_balance, created_at)
VALUES ('default', 10000.0, :created_at);

-- 4.2 Default chat state (empty rolling summary).
INSERT OR IGNORE INTO chat_state (user_id, summary, updated_at)
VALUES ('default', '', NULL);

-- 4.3 Default watchlist: 10 tickers from PLAN.md §7 "Default Seed Data".
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_aapl,  'default', 'AAPL',  :added_at);
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_googl, 'default', 'GOOGL', :added_at);
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_msft,  'default', 'MSFT',  :added_at);
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_amzn,  'default', 'AMZN',  :added_at);
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_tsla,  'default', 'TSLA',  :added_at);
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_nvda,  'default', 'NVDA',  :added_at);
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_meta,  'default', 'META',  :added_at);
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_jpm,   'default', 'JPM',   :added_at);
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_v,     'default', 'V',     :added_at);
INSERT OR IGNORE INTO watchlist (id, user_id, ticker, added_at) VALUES (:id_nflx,  'default', 'NFLX',  :added_at);
```

Each `:id_*` is a fresh UUID generated at seed time (the `UNIQUE (user_id, ticker)` constraint guarantees idempotency, so the UUIDs themselves are not required to be stable across reseeds).

Seed totals: **1** `users_profile` row, **1** `chat_state` row, **10** `watchlist` rows = **12** rows total. Tables `positions`, `trades`, `portfolio_snapshots`, `price_ticks`, `chat_messages` start empty by design.

## 5. Lazy initialization contract

Database initialization runs **exactly once per process**, inside the FastAPI lifespan startup hook (PLAN.md §7 "SQLite with Lazy Initialization"). The entry point is `init_database()` in `backend/app/db/init.py`. Behavior:

1. Resolve the database path from `FINALLY_DB_PATH` (default: `/app/db/finally.db`; fallback to a project-local path for tests). Create the parent directory if missing.
2. Open a connection and execute every `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` statement from §1 and §2. This is safe whether the file is brand new, partially populated, or fully populated.
3. Run the §4 `INSERT OR IGNORE` seed statements. If the rows already exist, this is a no-op.
4. Commit and close the bootstrap connection. Subsequent request handlers use `get_connection()` for per-request connections.

Because every DDL uses `IF NOT EXISTS` and every seed uses `INSERT OR IGNORE`, `init_database()` is fully idempotent: re-running it against an existing database is a cheap no-op, and starting against a missing file produces a clean, seeded database with no migration step. The server only accepts connections after init completes, so there is no first-request cold-start penalty.
