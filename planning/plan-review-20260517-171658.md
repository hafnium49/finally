## Findings

### High: Resolved review notes remain in the active plan and contradict the spec

`planning/PLAN.md:550` keeps a full "Review Notes" section described as a working list to triage before the next agent proceeds, but most items are already marked resolved in the same section (`planning/PLAN.md:556-604`). Worse, the final insight block still says the chat/trade boundary is underspecified and that SSE behavior is still described as the old push-every-500ms model (`planning/PLAN.md:610-613`), even though sections 6 and 9 now define those decisions (`planning/PLAN.md:191-193`, `planning/PLAN.md:340-407`).

This makes the plan self-contradictory: a future agent can reasonably treat section 13 as still-open work and override decisions already made earlier in the document. Move resolved notes to an archive, or rewrite section 13 so it contains only genuinely open decisions.

### Medium: Chat summary persistence is required but not actually specified

Section 9 requires old chat messages to be represented by a rolling summary and says that summary must survive across requests (`planning/PLAN.md:332-338`). The schema in section 7 only defines `chat_messages` with `role`, `content`, and `actions` (`planning/PLAN.md:262-268`), and the summary storage is left as "e.g., a `summary` row ... or JSON in the `users_profile` row" (`planning/PLAN.md:336`).

That is not enough for independent backend and chat agents to converge. The plan should pick one storage contract, such as a `chat_state(user_id primary key, summary text, updated_at text)` table, or add a concrete `conversation_summary` column to `users_profile`.

### Medium: SSE push-on-change and keepalive behavior are stated as if guaranteed, but the current market code does not implement both guarantees

The plan says the SSE generator only emits when a ticker's cached price has actually changed, and that a keepalive comment is sent about every 15 seconds (`planning/PLAN.md:191-192`). In the current code, `PriceCache.update()` increments `_version` on every update, even if the rounded price is unchanged (`backend/app/market/cache.py:23-42`), and `_generate_events()` never emits a keepalive comment when no version change occurs (`backend/app/market/stream.py:75-85`).

If this plan is intended as the target contract, call out that `PriceCache.update()` must be idempotent for same-value updates and that `_generate_events()` still needs a timed keepalive path. If it is intended to describe existing behavior, section 6 is inaccurate.

### Medium: LLM implementation instructions depend on an unavailable or non-portable agent skill

The plan instructs agents to "use cerebras-inference skill" for LiteLLM/OpenRouter calls (`planning/PLAN.md:313`, `planning/PLAN.md:324`). That skill is not in the available Codex skills for this workspace. There is a `.claude/skills/cerebras` directory, but the plan is written as a project-wide agent contract, so a Codex agent cannot follow that instruction as written.

Replace the skill dependency with concrete implementation requirements: package dependency, LiteLLM call shape, model/provider string, structured-output schema enforcement, error handling, and test/mock behavior. If a Claude-only skill remains useful, mark it as optional and agent-specific.

### Low: The documented bootstrap files are not present in the repository

The directory tree presents `frontend/`, `scripts/`, `test/`, `db/`, `Dockerfile`, `docker-compose.yml`, and `.env.example` as part of the project structure (`planning/PLAN.md:89-116`). The current repository only has the backend, planning docs, `.env`, and supporting review/plugin files; `.env.example`, `Dockerfile`, and `docker-compose.yml` are absent.

This is fine if section 4 is explicitly a target structure, but it currently reads like the existing repo layout. Label missing items as planned deliverables or add them before downstream agents rely on them.

## Test Gaps / Residual Risk

No test suite was run because this was a documentation review. The main residual risk is that `PLAN.md` mixes target architecture, current implementation notes, and resolved review history in one active spec, which can send future agents in conflicting directions.
